# История правок — nn_chat (бэкенд + web)

Человекочитаемый журнал заметных изменений. Технические детали — в git-коммитах.

## 2026-08-08

### Задачи заказов, ответственные
- У задачи появилась привязка к заказу (`todo_order_id`) и ответственные (`todo_assignees`, их может быть несколько) — миграция `20260808_000043`.
- **Видимость заказной задачи = видимость самого заказа**: её видит любой, кому виден заказ (те же склады и статусы, что в СРМ), а не только автор. Задача без заказа остаётся личной — автор и назначенные ответственные. Привязать задачу к недоступному заказу нельзя (404).
- Вести задачу (править, закрывать) может любой, кому она видна; **удалять — только автор или админ**, как с сообщениями чата.
- Задачи едут внутри карточки заказа (`order.todos`) — из них рисуется блок «Задачи» в приложении и бабл с количеством в списках СРМ. Любое изменение задачи пересылает карточку заказа по SSE, поэтому счётчик обновляется в реалтайме.
- При назначении ответственным уходит пуш — только тем, кого назначили именно этим запросом (повторное сохранение того же состава молчит).
- Заказ удалён — задачи остаются и просто теряют привязку (FK `SET NULL`), работа не пропадает.

## 2026-08-07

### Тудулист («Задачи»)
- Личный менеджер задач: `todo_lists`, `todos`, `todo_subtasks` (миграция `20260807_000042`), эндпоинты `GET/POST/PUT/DELETE /todos`, `PUT /todos/reorder`, `POST/PUT/DELETE /todo-lists`.
- Умные списки (Входящие, Сегодня, Запланировано, Когда-нибудь, Архив) в базе **не хранятся** — считаются клиентом по полям задачи, поэтому доска отдаётся одним запросом.
- Сроки — дата **со временем** (`todo_do_at` / `todo_deadline_at`, хранятся в UTC): клиент шлёт ISO со смещением, сервер приводит к UTC.
- Задачи личные: чужие не видны и не редактируются (404). Новый ключ раздела **`todo`** в `GRANTABLE_SECTIONS` — в админке «Задачи» рядом с чат/СРМ/прайс; гейтит только приложение, веб-экрана у тудулиста нет.

### Закреплённые сообщения чата заказа
- `PUT /orders/{id}/comments/{id}/pin` — закрепить/открепить сообщение, **не больше 3 на заказ** (иначе 400). Флаг `order_comment_is_pinned` (миграция `20260807_000041`) приходит в карточке заказа.
- Закреплять может любой, кто видит заказ (в отличие от правки и удаления, где права по автору). Действие пишется в аудит (`order.comment.pin`) и в историю заказа; карточка заказа пересылается по SSE.

## 2026-08-06

### Новый статус товара «Упаковано»
- В справочник статусов позиций добавлен **«Упаковано»** (сид, отдельного действия не нужно) — финальный шаг сборки в «Отгрузках»: кнопка «Упаковать» переводит позицию в него, а заказ считается собранным, когда упакованы все неотменённые позиции.
- Сплит заказа («На сборку») теперь считает «Упаковано» готовым к отгрузке наравне с «В наличии»/«Собрано» — упакованное не уезжает в дубль. То же правило в вебе.

### Служебный пуш
- `POST /notifications/system` (`{title, body, event_type}`) — уведомление «от системы» на все активные устройства. Слать может админ или сервисный логин из `SYSTEM_PUSH_LOGINS` (по умолчанию `nufnaf.ru`). Используется прайсом: «прайс обновлён» после всех этапов. Тап по такому пушу никуда не ведёт (`entity_id = 0`), приложение просто показывает текст.

### Способ заказа стал необязательным
- `orders.order_method_id` теперь nullable (миграция `20260806_000040`): заказ можно создать и сохранить **без способа заказа** — так приходят заказы с сайта, способ выбирает менеджер. Раньше поле было обязательным и приходилось ставить заглушку «Курьер», которая вводила в заблуждение.
- Подспособ без способа теперь ошибка (400). Веб: способ в карточке/строке просто не отображается, если не выбран.
- **Важно для приложения:** iOS до билда 36 не умеет читать заказ без способа (поле было обязательным в модели) — прежде чем заказы начнут приходить без способа, нужен билд 36 и поднятый `min_supported_ios_build`.

### Оплата заказа
- У заказа появилась **отметка об оплате**: `orders.order_paid_at` + кто отметил (`order_paid_by_user_id`), миграция `20260806_000039`. В API заказа — `order_paid`, `order_paid_at`, `order_paid_by_*` (в том числе в карточках заказа внутри чата).
- Новый эндпоинт `PUT /orders/{id}/payment` (`{"order_paid": true|false}`): права те же, что на изменение заказа; пишется в аудит и историю заказа отдельной строкой («отметил заказ оплаченным» / «снял отметку об оплате»), карточка обновляется по SSE.
- **Веб пока не трогали** — отметка ставится из приложения (кнопка у «Итого» в разделах «Все заказы» и «Отгрузки»).

### Прайс — Price update
- В список этапов приёма CL-прайса добавлен **Этап 5 «Обновление прайс-листа на платформе NufNaf.ru»**: пока идёт миграция, карточка показывает сообщение платформы и процент (Обработано/Всего позиций), после — числа прогона (Обновлено, Пропущено, строк с ошибками). Кнопка «Обновить платформу» перезапускает этап вручную (`POST /price-api/api/price/nufnaf-sync`). Бэкенд — в nn_price.

- **Веб**: селектор «Канал» в форме заказа (перед складом) + автоподстановка из клиента; канал первым в шапке заказа (`Розница · TG · Окто · СДЭК`); новая вкладка **«Каналы»** в Справочниках (добавление/переименование).

### Заказы — поиск по номеру
- Поиск в списке заказов теперь матчит и **номер заказа** (`order_id`), если запрос числовой; текстовый поиск по клиенту/информации — как раньше. Плейсхолдер в вебе обновлён.

### Форс-апдейт iOS — «Админка»
- Настройка `min_supported_ios_build` (таблица `app_settings`, миграция `20260722_000038`): отдаётся в `/reference-data`, меняется через `PUT /app-settings` (только админ). `0` = гейт выключен.
- **Веб**: новый раздел меню **«Админка»** (только для админов) с полем «Минимальный билд iOS». Приложение с билдом ниже блокируется экраном «Обновите приложение», пока не обновится. Форс-апдейт теперь = поднять число в панели (работает с билдов, где гейт уже встроен, т.е. 34+).

## 2026-07-04

### Права доступа — гибкая система
- **Права по складам**: у каждого склада, к которому есть доступ, — своя настройка: область видимости (только свои / весь склад), можно ли создавать, область редактирования и удаления (свои / весь склад). Полный набор: отсутствие склада = нет доступа. Хранится в `user_establishment_roles`.
- **Разделы меню / режимы приложения** (`users.user_sections`): что видит пользователь — чат / СРМ / прайс + подразделы СРМ (заказы, товары, инвентаризация, регистрации, контакты). `null` = все разделы, пустой список = нет доступа. Веб прячет пункты меню, приложение гейтит режимы (свайп-пейджер показывает только доступные).
- **Раздаёт права только админ** (страница «Пользователи» в вебе). Админ обходит все проверки. **Вход в веб** открыт любому, у кого есть хотя бы один раздел или роль на складе (раньше — только админ).
- **Отдельная страница пользователя**: личные данные (имя/фамилия/возраст/адрес), кнопки доступа/статуса в шапке, режимы и разделы, права по каждому складу.
- **Админ может удалять сообщения в чате любого пользователя** (не только свои).

### Реалтайм-права
- Смена прав по складам или разделов/статуса пользователя рассылает SSE-событие `user_updated`; веб и приложение перечитывают `/me` и применяют доступ **на лету, без перезахода** (меню/режимы обновляются сразу). Отзыв доступа к текущему режиму в приложении возвращает на «Чат».

### Лента чата — фильтрация карточек по складам
- Карточки заказов/инвентаризаций/приёмок в ленте чата (`/messages`, `/messages/sync`) теперь **фильтруются по правам склада** (те же `can_view_document`, что и в списках). Раньше фид отдавал все карточки всем — в приложении, где раздел СРМ строится из карточек чата, пользователь видел заказы недоступных складов. Обычные текстовые сообщения остаются общими; админ обходит фильтр. Приложение по `user_updated` перезабирает ленту с нуля, чтобы карточки отозванного склада исчезли реалтайм.

### Web — чат
- Поле ввода сообщения **авто-растягивается** под многострочный текст (как textfield в приложении): растёт по строкам до `max-height`, дальше — внутренний скролл; после отправки сжимается обратно.

### Web — заказы
- **Дата заказа в 2 строки**; над датой — **ФИО создателя** заказа.
- **Трек СДЭК**: по тапу на номер — меню «Скопировать трек / Пересоздать накладную» (убрана отдельная кнопка «Пересоздать» из строки).
- **«Действие»** — выпадающий список у свёрнутых заказов (вместо одиночной «Удалить»): удалить отмеченные, скопировать позиции (с количеством и ценой / просто список).
- **Колонка «Итого»** фиксированной ширины: мультивалютное значение в одну строку с многоточием — не смещает соседние колонки (полное значение в подсказке).
- **Иконка чата заказа**: красноватая при непрочитанных, зеленоватая когда все прочитаны, + мелкий бейдж-счётчик. Оверлей чата крупнее и фиксированного размера, сообщения прижаты к низу над полем ввода.

### Каталог / производительность
- **Фоновая гидратация прайса** при интерактивном поиске: поиск сразу отдаёт локальные результаты, свежий CL из `nn_vla` подтягивается отдельным потоком (быстрый «холодный» первый поиск при создании заказа). Переиспользуемый HTTP-клиент + TTL-кэш запросов.

## 2026-07-03

### СДЭК (доставка) — новая интеграция
- **Создание накладной** (`POST /cdek/orders/{id}/waybill`): получатель, город получателя и ПВЗ (поиск по названию/адресу — без кодов), курьер/ПВЗ, габариты, тариф, доп. услуги (страхование, СМС, наложенный платёж, оплата доставки отправитель/получатель). Обе печатные формы (накладная + ШК) как **PDF падают в чат заказа** от системного пользователя `cdek_helper`.
- **Отправитель**: город + опциональный **ПВЗ сдачи** (`shipment_point`) — сдаём в ПВЗ или курьер. На проде имя/адрес отправителя берутся из договора СДЭК (не шлём); на тесте — заглушка. `GET /cdek/defaults` — последний использованный ПВЗ сдачи для подстановки по умолчанию.
- **Статусы**: авто через вебхук (`POST /cdek/webhook`, публичный, регистрируется на старте по `CDEK_WEBHOOK_URL`) + пуллинг `GET /cdek/orders/{id}/status`.
- **Пересоздание/сброс** (`DELETE /cdek/orders/{id}/waybill`): удаляет заказ в СДЭК и чистит трек/статус (данные получателя сохраняет) — спасает от тупика при невалидной накладной («Некорректный заказ»).
- **Префилл**: данные СДЭК клиента подставляются из его прошлых заказов (`GET /cdek/prefill`).
- Ключи/среда: `CDEK_BASE_URL` (тест `api.edu.cdek.ru` / прод `api.cdek.ru`), `CDEK_ACCOUNT`/`CDEK_SECURE` в GitHub-секретах.

### Web — заказы
- **Чат заказа** в оверлее (иконка 💬 в строке): просмотр и отправка сообщений внутреннего чата заказа, realtime-обновление, вложения (фото/файлы, вкл. PDF-накладные от `cdek_helper`) read-only.
- **Массовая смена статуса заказов**: у свёрнутых строк — чекбокс; отмеченным заказам меняем статус тем же bulk-селектором, что и позиции (опции переключаются на статусы заказа).
- СДЭК-накладная: оверлей создания (поля получателя/отправителя/ПВЗ/тарифа/услуг), «Пересоздать» в строке.

### Инфраструктура / конфигурация
- Стандартизирован нейминг compose: `docker-compose.yml` — локальный запуск, `docker-compose.prod.yml` — сервер. Локальный стек читает `.env` (через `${VAR:-default}`, работает и без файла); `.env.example` — локальный шаблон, прод-конфиг — только в GitHub-секрете `PRODUCTION_ENV_FILE` (переменные описаны в `DEPLOYMENT.md`).
- dev-compose: `pull_policy: never` для `backend`/`seed` (локальный образ собирается, а не тянется из реестра).

### Заказы
- Частичная отгрузка (`POST /orders/{id}/split`): в заказе остаются и «В наличии», и уже «Собрано» (раньше «Собрано» уезжало в дубль).

## 2026-06-27

### Авторизация
- Грейс-период для refresh-токена: при ротации прежний токен ещё ~60с валиден, чтобы прерванный/повторный/параллельный рефреш не выкидывал на логин (чинило разлогин при тапе по пушу). Колонки `session_prev_token`/`session_prev_token_expires_at`, миграция `20260627_000027`.

### Realtime / синхронизация (фаза 2, бэкенд)
- Инкрементальный синк: `GET /messages/sync?cursor&limit` — изменения с курсора (живые сообщения + тумбстоуны удалённых). Колонки `message_updated_at` (+индекс) и `message_deleted_at` (soft-delete), миграция `20260627_000028`.
- SSE: `GET /messages/stream` + внутрипроцессный брокер (один воркер). События `created/updated/deleted`.
- Карточка чата = единица синка: при изменении заказа/инвентаризации/приёмки/статуса «трогается» её сообщение и эмитится SSE — статусы/позиции расходятся через один канал.
- nginx: отдельный `location` для SSE-стрима без буферизации.

### Web realtime (чат, заказы, документы)
- Один app-wide SSE-канал (`fetch`+ReadableStream, т.к. нативный EventSource не шлёт Bearer). Страницы «Заказы»/«Документы» и чат обновляются вживую.
- Резервный поллинг (5с) — гарантирует доставку app→web, когда браузерный SSE буферится прокси.
- Обновление токена на web (хранение refresh, coalesced refresh + ретрай на 401) — web больше не теряет realtime и не разлогинивает через 30 минут.
- Мгновенная очистка поля ввода при отправке сообщения.
- Фикс «залипшей» строки заказа: пере-синхронизация локального стейта строки из рефетча (цена/позиции/покупатель обновлялись только после F5; статус заказа — обновлялся).

### Деплой
- Деплой по push в `main` (GitHub Actions): pytest → сборка образов backend+web → выкатка на VPS, миграции применяются автоматически.
